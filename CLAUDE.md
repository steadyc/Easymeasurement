## Development Workflow

### Branching Strategy

- **Main branch:** `main` (production-ready code)
- **Feature branches:** `feature/<short-description>`
- **Bug fix branches:** `fix/<short-description>`
- **Claude-initiated branches:** `claude/<description>-<session-id>` (auto-generated by Claude Code)

### Commit Message Convention

Use [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <short summary>

[optional body]

[optional footer]
```

**Types:**
- `feat` — new feature
- `fix` — bug fix
- `docs` — documentation only
- `refactor` — code change that is neither fix nor feature
- `test` — adding or updating tests
- `chore` — build process or tooling changes
- `ci` — CI/CD configuration changes

**Examples:**
```
feat(measurements): add bulk import from CSV
fix(api): handle null values in measurement endpoint
docs: update CLAUDE.md with project structure
```

### Pull Request Process

1. Create a branch from `main`
2. Make focused, well-tested changes
3. Write a clear PR description explaining the *why*, not just the *what*
4. Ensure all tests pass before requesting review
5. Request at least one human review for non-trivial changes
6. Squash-merge into `main`

## Code Conventions

### General Principles

- **Simplicity over cleverness** — write code that is easy to read and modify
- **No premature abstraction** — don't generalize until you have three or more concrete cases
- **Explicit over implicit** — prefer clear naming and structure over magic
- **Minimal surface area** — expose only what is necessary from modules/functions

### File & Directory Naming

> Define once the project language and framework are chosen.

- Use `kebab-case` for file names in web projects (e.g., `user-profile.tsx`)
- Use `snake_case` for file names in Python projects (e.g., `user_profile.py`)
- Use `PascalCase` for React components (e.g., `UserProfile.tsx`)

### Variables & Functions

- Prefer descriptive names over comments: `calculateTotalMeasurement()` vs `calc()`
- Functions should do one thing and be named for what they *do*, not what they *are*
- Constants in `UPPER_SNAKE_CASE`

### Error Handling

- Validate at system boundaries (user input, external APIs, file reads)
- Do not swallow errors silently — log or propagate with context
- Prefer early returns / guard clauses over deeply nested conditionals

## AI Assistant Guidelines

When working as an AI assistant in this repository:

### Do
- Read existing code before proposing changes
- Make minimal, focused edits that address exactly what was asked
- Follow the commit message convention above
- Update `CLAUDE.md` when you discover new patterns or add significant structure
- Ask clarifying questions when requirements are ambiguous

### Don't
- Add features, refactors, or "improvements" that weren't requested
- Add unnecessary comments, docstrings, or type annotations to code you didn't change
- Create new files when editing an existing one would suffice
- Introduce backwards-compatibility hacks for code that has no external consumers
- Push to `main` directly — always use a feature/claude branch

### Branch Naming (Claude Code)
Claude-initiated branches follow the pattern:
```
claude/<short-task-description>-<session-id>
```
Example: `claude/add-claude-documentation-HCoed`
